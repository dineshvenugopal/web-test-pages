Automation Form Filler Test Bed

Comprehensive fixture for discovering, filling, validating, and submitting web forms. Each info button describes the behavior an automation tool should detect. Use data-scenario, name, id, labels, ARIA attributes, and native properties as test signals.

Important: A form filler should distinguish native controls from custom widgets, skip non-fillable controls, wait for async state changes, preserve user data, dispatch input/change events, and report blocked or invalid fields.

2. Choices, text areas, and multiple values
Radio group
Same-name radios are one logical field. Select exactly one unless optional; labels can be easier than tiny inputs.
Checkboxes
Checkboxes with the same name produce multiple values. An unchecked checkbox is omitted from FormData.
Required checkbox state is checked/unchecked, not a text value.
Map visible labels to option values, honor disabled options and optgroups, and dispatch change.
Multiple selected options serialize as repeated keys. Do not replace the select with one string.
Respect maxlength, newlines, normalization, and character counters.
Datalist is a suggestion list, not a constrained select. Users may enter a value not in the list.
3. State, visibility, and constraints
Readonly controls are focusable and submitted, but cannot be edited. Report rather than silently removing readonly.
Disabled controls cannot receive focus and are omitted from submission. Check disabled ancestor fieldsets too.
ARIA-disabled is not native disabled: it may still be focusable and writable. Treat it as a framework constraint and report it.
Inspect required, pattern, title, min/max, minlength/maxlength, and custom validity.
A hidden input is submitted but not user-fillable.
Distinguish type=hidden from CSS-hidden controls and honeypots. Hidden values may be IDs or CSRF state.
Intentionally invisible bot trap; leave empty.
Check computed visibility, dimensions, tabindex, aria-hidden, and off-screen styles before filling.
